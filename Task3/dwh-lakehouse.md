# DWH и Data Lakehouse

## Сравнение

| Критерий | PostgreSQL DWH | Data Lakehouse |
| --- | ---| --- |
| Основное назначение | Регламентированная отчётность и BI | Большая история, события и аналитика |
| Данные | Структурированные и согласованные | Структурированные, событийные, исторические, полуструктурированные |
| Хранение | PostgreSQL | S3 / объектное хранилище |
| Табличная модель | Реляционные таблицы | Apache Iceberg поверх файлов |
| Обработка | ETL | ETL / ELT / Streaming |
| SQL | PostgreSQL | Trino |
| Основная сильная сторона | Стабильная модель отчётности | Масштабируемость и гибкость |
| Основное ограничение | Масштабирование больших исторических и событийных наборов | Более сложная архитектура и эксплуатация |

## Выбранный подход

### Через 3 месяца

PostgreSQL DWH + MDM + Airflow

PostgreSQL используется для первого согласованного аналитического контура и минимальных BI-витрин.

### Через 12 месяцев

Гибрид PostgreSQL DWH + Data Lakehouse

- DWH сохраняет регламентированные и согласованные данные
- Lakehouse хранит большие исторические и событийные наборы
- DataHub обеспечивает каталог и lineage
- Доменные команды публикуют Data Products

## Роль Apache Iceberg

Apache Iceberg создаёт управляемые таблицы поверх файлов объектного хранилища

Он хранит метаданные о:
- файлах таблицы
- актуальной схеме
- текущей версии
- предыдущих снимках

Таким образом, объектное хранилище превращается из набора файлов в управляемый табличный слой.

## Роль Trino

Trino — распределённый SQL-движок для Lakehouse.

- получает SQL-запрос
- читает метаданные Iceberg
- определяет необходимые файлы
- распределяет вычисления между рабочими узлами
- возвращает результат потребителю

Trino не хранит данные и не заменяет S3 или Iceberg

## Распределение данных

| Данные | Хранилище | Почему |
| --- | --- | --- |
| Регуляторные показатели | DWH | Нужна стабильная и воспроизводимая отчётность |
| Согласованные BI-витрины | DWH | Структурированные данные и предсказуемые запросы |
| Клиентские аналитические измерения | DWH | Используются во множестве отчётов |
| Большая история транзакций | Lakehouse | Большой объём и исторический анализ |
| Карточные события | Lakehouse | Потоковые событийные данные |
| История изменений | Lakehouse | Необходимо сохранять версии и историю |
| Архивные данные RetailBank | Lakehouse / Object Storage | Большой объём исходных исторических данных |
| Полуструктурированные данные | Lakehouse | Не требуют предварительного сведения к строгой DWH-схеме |

## Ограничения

### PostgreSQL DWH
- не предназначен для неограниченного роста больших событийных наборов
- сырые данные необходимо приводить к согласованной модели
- тяжёлые исторические запросы увеличивают нагрузку
- требуется управление staging/core/data marts и повторными загрузками

### Data Lakehouse
- больше инфраструктурных компонентов
- необходимо управлять качеством Bronze/Silver/Gold
- требуется обслуживание метаданных и Iceberg-снимков
- качество Lakehouse зависит от governance, каталогизации и владельцев
- Trino добавляет отдельный вычислительный слой, который необходимо эксплуатировать

## Вывод

Для FinUnion + RetailBank оптимален гибридный подход.

PostgreSQL DWH отвечает за доверенные структурированные данные, BI и регламентированную отчётность. Data Lakehouse на S3 + Apache Iceberg + Trino отвечает за большую историю, события и более гибкие аналитические сценарии. Такое разделение позволяет не превращать DWH в универсальное хранилище всех данных и одновременно не переносить критичную отчётность в более сложный Lakehouse-контур.
